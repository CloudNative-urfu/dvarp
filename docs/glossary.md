# Глоссарий терминов проекта

Свод терминов, аббревиатур, жаргонных слов и словосочетаний обоих репозиториев воркспейса — `dvarp` и [`agent-research-factory`](https://github.com/CloudNative-urfu/agent-research-factory) (ниже — «фабрика»).

**Цель:** единый словарь команды и зафиксированные соглашения по терминологии.

**Как читать ссылки.** Путь без префикса (`docs/…`, `README.md`) — файл этого репозитория;
префикс `фабрика:` — путь внутри `agent-research-factory` (`фабрика: docs/METHODOLOGY.md`).

**Как оформлять термины.** Русское слово — основная форма; при первом употреблении в тексте
английский оригинал даётся в скобках (так же ведётся черновик статьи — `docs/paper/draft.md`).
Если термин в старых доках расходится с разделом 1 — приоритет у раздела 1; новые тексты
пишутся по канону, старые доки переписывать массово не требуется.

## 1. Соглашения по терминологии (канон)

### 1.1. Фабрика / полигон — это автооценщик чьих-то процессов

**Фабрика** и **полигон** — слова об одном: сторона, которая *автоматически оценивает* чужие
процессы/решения, а не является самим оцениваемым процессом. Канон: это всё, что в соседнем
репозитории [`agent-research-factory`](https://github.com/CloudNative-urfu/agent-research-factory),
и только оно.

- **Фабрика** (Agent Research Factory) — конвейер автономных исследовательских кампаний
  (постановка → идеи → малый пилот → реализация → измерения → независимая критика), который
  и проводит эту оценку (`фабрика: README.md`).
- **Полигон** — система для автоматизированного исследования безопасности стороннего сервиса
  в пределах заданных правил, ограничений и бюджета с целью проверки защиты стороннего
  сервиса; в доках фабрики так называется собираемый ею оценивающий стенд
  (`фабрика: docs/DEEP_CASE.md` — «сборка полигона по докам кейса»). Сторонний сервис в каноне
  обозначается «СС», основные термины полигона — в 1.5.

Антоним пары «фабрика/полигон» — **прототип/стенд** (1.2): наш симулируемый процесс, на котором
полигон проводит оценку. В старых доках этого репозитория «полигоном» часто назван наш стенд —
по канону такие употребления следует читать как «прототип»/«стенд».

### 1.2. Прототип — наш симулируемый процесс для статьи

**Прототип** — моделируемый бизнес-процесс обработки возвратов интернет-магазина на
синтетических данных вместе с обвязками для исследования (стенд). Он существует *только*
для исследования и статьи: это не продукт и не оценщик, а измеряемая среда, внутри которой
атакуют и защищаются. Канон: это всё, что в репозитории `dvarp` (`docs/guardrails-as-a-vector-of-attack.md`
§6.1; в фабрике тот же объект — «существующий прототип» и «магазин»,
`фабрика: nix/_research/COEVOLUTION.md`).

**Стенд = прототип**: только наш бизнес-процесс с обвязками для исследования. Стендом фабрику
и полигон не называем.

### 1.3. Два уровня агентов в полигоне

Агенты делятся на два уровня — по отношению к полигону (фабрике).

**Внешние (внешнеуровневые) агенты** — разные Claude, которые меняют инфраструктуру и
осуществляют контроль. Канон: это **исследователь** и **критик** фабрики — и только они:

- **исследователь (researcher)** — агент-исполнитель стадий конвейера; backend — Claude Code
  (Opus) или OpenCode (`фабрика: nix/_research/README.md` §2);
- **критик (critic)** — независимый агент-ревизор, отдельная сессия с неизменяемой копией
  материалов (`фабрика: nix/_research/critic.md`).

Контроллер (`factory.py`), автопилот и монитор — программы, а не агенты: они обслуживают
внешний уровень (оркестрация, проверки, наблюдение), но в понятие «внешние агенты» не входят.

**Внутренние агенты** — лёгкие развёртываемые агенты, которые атакуют и защищаются. Они
работают *внутри* прототипа и взаимодействуют только через канал. В существующих доках им
соответствуют:

- **атакующий (attacker)** / атакующая сторона (`docs/guardrails-as-a-vector-of-attack.md` §4.1;
  `фабрика: nix/_research/COEVOLUTION.md` §A);
- **защитник (defender)** / защищаемая сторона — LLM-агент + исполнитель
  (`docs/guardrails-as-a-vector-of-attack.md` §4.1; `фабрика: nix/_research/COEVOLUTION.md` §A).

Канон полигона: атакующий — «атакующий агент (АГ)», работающий через свой харнес (1.5).

Внутренние агенты исполняются на экспериментальной модели (`qwen/qwen3.5-9b` через
фиксированный маршрут `darkbloom/fp4`, `фабрика: README.md`) — это отдельный ресурс, не модель
внешних агентов.

### 1.4. Правила употребления

- Русская форма + английский оригинал в скобках при первом употреблении.
- Единые формы: «гвардрейл» (не «guardrail» внутри русского текста), «базовая линия»,
  «прогон», «эскалация», «исполнитель», «оценщик», «полигон», «прототип», «харнес».
- «Стенд» = «прототип» (1.2): наш бизнес-процесс с обвязками для исследования. Стендом не
  называем фабрику/полигон; в старых доках `docs/research-cycles/` «стенд» иногда означает
  установку конкретного цикла — по канону читать как «прототип/стенд».
- «Кампания» — работа фабрики; «цикл» — одна итерация кампании (см. раздел 2).

### 1.5. Термины полигона (канон)

Определения ниже зафиксированы автором задачи и имеют приоритет над другими употреблениями
этих слов в данном глоссарии и в доках. Соответствие текущей реализации фабрики отмечено
только там, где оно уверенное.

- **Полигон** — система для автоматизированного исследования безопасности стороннего сервиса
  в пределах заданных правил, ограничений и бюджета с целью проверки защиты стороннего
  сервиса (см. также 1.1).
- **Атакующий агент (АГ)** — агент, имеющий харнес для ведения тестирования (пентестинга)
  стороннего сервиса. Канон: внутренний агент полигона (1.3).
- **Харнес (harness)** — программная часть АГ, которая управляет выполнением операций,
  инструментами и расходованием ресурсов.
- **Сторонний сервис (СС)** — сервис, подключаемый к полигону для исследования в рамках
  исследовательской кампании. СС может быть развёрнут непосредственно в инфраструктуре
  полигона либо работать во внешней среде — тогда взаимодействие осуществляется через
  предоставленные интерфейсы, например API. Наш прототип (1.2) — СС, развёрнутый в
  инфраструктуре полигона.
- **Интерфейс** — контрактный способ взаимодействия между АГ и СС, задающий допустимые
  операции, форматы данных, ошибки и сигналы обратной связи, включая отсутствие ответа.
- **Инструменты (tools)** — функция харнеса с явным контрактом, которую может вызвать LLM;
  конкретные Tools для АГ.
- **Кампания** — весь исследовательский запуск от старта до финиша в рамках тестирования
  конкретного СС: одна целостная программа проверки, заданная КИК. Внутри кампании может
  быть много эпизодов (ЭК), но все они работают в рамках одной КИК: одного бюджета, одной
  памяти и т.д.
- **Чекпоинт кампании** — сохранённый слепок кампании, содержащий всю содержательную
  информацию об этой кампании; фактически память и данные кампании. Чекпоинт — не обязательно
  слепок ЭК: это может быть слепок этапа внутри ЭК.
- **Форк кампании** — запуск кампании не с последнего сохранённого чекпоинта. Запуск с
  последнего чекпоинта — всего лишь продолжение текущей кампании, форком не является.
- **Эпизод кампании (ЭК)** — одна попытка проверить конкретную гипотезу, провести внутренний
  эксперимент, находящийся внутри глобального исследования, заданного КИК. Подразумевает
  завершённый блок, который может включать несколько действий агента, направленных на
  подтверждение или опровержение гипотезы.
- **Бюджет кампании (БК)** — набор лимитов ресурсов, которые агент может потратить на
  отдельный ЭК или в целом на всю кампанию. Основные типы:
  - *бюджет взаимодействий с прототипом (в запросах)* — например, максимум N запросов к
    исследуемому СС за кампанию;
  - *бюджет токенов* — сколько токенов АГ может потратить на собственное планирование, анализ
    ответов, работу с памятью и другие операции LLM; при необходимости отдельно учитываются
    токены запросов к СС;
  - *временной бюджет* — например, максимальная продолжительность кампании; важно учитывать
    как общее время, так и таймауты отдельных операций;
  - *вычислительный или денежный бюджет* — например, максимальная стоимость API-вызовов;
  - *бюджет эпизодов* — максимальное количество исследовательских эпизодов или попыток
    проверить различные гипотезы в рамках одной кампании.

  По жёсткости бюджеты делятся на два типа: *жёсткие БК* — лимиты, превышать которые
  запрещено; харнес должен предотвращать их превышение, а когда лимит исчерпан и продолжать
  нельзя, исследование прерывается с сигналом `INTERRUPTED`; *мягкие БК* — сигналы
  предупреждающего характера, не предполагающие моментального прекращения исследования.
- **Конфигурация исследовательской кампании (КИК)** — неизменяемый файл, который описывает:
  что исследуем; какие интерфейсы доступны; настройки памяти агента и чекпоинт, с которого
  стартуем; какой бюджет кампании; какие ограничения кампании; как определяем результат
  кампании. В реализации фабрики этому соответствует конфиг кампании `campaign.json`.

## 2. Фабрика и конвейер кампаний

- **Фабрика (Agent Research Factory)** — автономный конвейер: постановка задачи → идеи →
  малый пилот → реализация → измерения → независимая критика; каждый цикл создаёт новую
  реализацию, используя память предыдущих результатов, а не копируя старый MVP
  (`фабрика: README.md`). Канон: 1.1.
- **Кампания (campaign)** — канон: весь исследовательский запуск от старта до финиша в рамках
  тестирования конкретного СС, заданный КИК (1.5). В реализации фабрики — каталог
  `~/.local/share/research-campaigns/<имя>` с конфигом `campaign.json` и состоянием
  `state.json`; исторические имена кампаний — `defense`, `dvarp` (`фабрика: docs/OPERATIONS.md`).
- **Цикл (cycle)** — полный проход конвейера по стадиям; новый цикл стартует в пустом
  `cycles/NN/work` и создаёт реализацию с нуля, получая память предыдущих через handoff
  (`фабрика: nix/_research/README.md` §5). Итоги циклов кампании defense описаны в
  `docs/research-cycles/cycle_1.md` … `cycle_9.md` и `docs/research-cycles/overall_cycle.md`.
- **Стадия (stage)** — шаг пайплайна: v1 — `research → plan → build → experiment → report →
  verify → review → confirm`; v2 добавляет `idea_review → pilot_plan → pilot → pilot_review`
  (`фабрика: docs/METHODOLOGY.md`, `фабрика: nix/_research/WORKFLOW-V2.md`).
- **v1 / v2** — версии процесса конвейера; v2 (opt-in, `pipeline_version: 2`) добавляет раннюю
  независимую критику и пилот с общим исполнителем запросов (`фабрика: nix/_research/WORKFLOW-V2.md`).
- **Контроллер (controller)** — программа `factory.py` / CLI `research-factory`, управляющая
  стадиями, попытками, лимитами и изоляцией; «состояние и архив контролирует программа, а не
  самооценка агента» (`фабрика: nix/_research/factory.py`). Не агент (1.3): программы
  обслуживают внешний уровень, но агентами не считаются.
- **Исследователь (researcher)** — внешний агент-исполнитель стадий (1.3). Друг от друга
  исследователь и критик отделяются сессиями и, по возможности, моделями.
- **Критик (critic) / независимая критика** — внешний агент-ревизор: получает неизменяемую
  копию материалов, выдаёт вердикт `accept/revise/pivot/blocked`, score 0..4, issues с
  severity/evidence/fix (`фабрика: nix/_research/critic.md`). Утрата «независимости критика»
  при переводе на общий бэкенд — открытая проблема кампании (`docs/research-cycles/overall_cycle.md`).
- **Пилот (pilot)** — малая проверка идеи до большого эксперимента (лимиты ~100 запросов /
  1800 сек): интерфейс, need-for-LLM, различимость механизма, выполнимость бюджета;
  «не является подтверждением эффективности» (`фабрика: nix/_research/WORKFLOW-V2.md`).
- **Ранний отсев (screened_out)** — завершение цикла без фиктивных измерений, если идея
  отклонена на `idea_review`/`pilot_review` (`фабрика: nix/_research/WORKFLOW-V2.md`).
- **Гейт (gate)** — обязательное булево условие приёмки: `reproducible`,
  `hypothesis_supported`, `useful`, `relevant`, `valid_evaluation`, `scenario_diversity`,
  `guardrail_depth` и др. (`фабрика: nix/_research/README.md` §4). В циклах 1–9 — серия
  замороженных шлюзов G0–G8, G-τ, G-break, resource gate (`docs/research-cycles/cycle_2.md`,
  `cycle_7.md`).
- **need-for-LLM** — обязательный гейт «LLM лучше детерминированного соперника»; в кампании
  defense не проходился пять циклов подряд (`docs/research-cycles/overall_cycle.md`).
- **Кандидаты (candidates)** — реализации, принятые критиком в `review`; ранжируются и
  независимо подтверждаются по очереди (`confirm`) до первого успешного
  (`фабрика: nix/_research/README.md` §4).
- **Вердикт (verdict)** — решение критика (`accept/revise/pivot/blocked`) или автопилота
  (`proceed/revise/pivot/stop/blocked`); `pivot/stop/blocked` — пауза цепочки, решение
  принимает оператор-человек (`фабрика: docs/AUTOPILOT.md`).
- **Handoff (handoff.json)** — «память предыдущих результатов»: факты, провалы, неизвестные,
  уроки (lessons) и критика прошлых циклов, передаваемые новому циклу; исходники прежнего MVP
  не копируются (`фабрика: nix/_research/README.md` §5). В dvarp-доках кампании — «17 уроков»
  c1-issue0…c7-issue1 (`docs/research-cycles/cycle_9.md`).
- **deep_case** — режим глубокой проработки кейса: готовая постановка из внешних документов
  доводится до исполняемой zero-версии полигона; гейтов нет, сбой ведёт к ремонту; пайплайн
  `decompose → build:<компонент> → integrate → fix → report → critique`
  (`фабрика: docs/DEEP_CASE.md`). Именно в этом режиме фабрика собирает полигон по докам
  этого репозитория.
- **Ремонт (repair / replan)** — повторные попытки шага deep_case: первая — `build`, далее
  `repair` с причиной; последняя — `replan`: сузить шаг до минимальной работающей версии,
  заглушка фиксируется в `artifacts/simplifications.json` (`фабрика: docs/DEEP_CASE.md`).
- **Zero-версия (zero)** — первая версия прототипа; далее она достраивается в одном каталоге
  `cycles/01/work`, а не пишется заново (`фабрика: docs/DEEP_CASE.md`,
  `фабрика: examples/deep_case.dvarp.md`).
- **Автопилот (autopilot) / автопереход** — `research-factory autopilot`: ждёт завершения
  кампании и независимой критики, запускает брейншторм улучшений + независимую оценку и
  создаёт следующую ревизию (`фабрика: docs/AUTOPILOT.md`).
- **Ревизия (revision)** — следующая версия решения в цепочке автопилота (`dvarp-revision-N`);
  получает проверенную baseline-копию и происхождение решения в `autopilot.json`
  (`фабрика: docs/AUTOPILOT.md`).
- **DVARP / coevolution (состязательная эволюция)** — программа эволюции атаки и защиты без
  доступа к внутренностям противника, с накоплением опыта обеими сторонами; этапы:
  I (инфраструктура магазина) → A (OS-изоляция) → B (строгая изоляция опыта) → C (лига
  замороженных версий) (`фабрика: nix/_research/COEVOLUTION.md`).
- **Оператор** — человек в контуре: операторские согласования (approvals) в магазине,
  операторские квитанции переходов стадий, решения при `pivot/stop/blocked`;
  **операторская остановка** — прекращение эксперимента человеком (`фабрика: nix/_research/COEVOLUTION.md`;
  «кампания ограничена семью циклами» — `docs/research-cycles/cycle_7.md`).
- **Экспериментальная модель** — отдельный ресурс, не модель исследователя/критика:
  `qwen/qwen3.5-9b`; ключ OpenRouter не авторизует исследователя и критика
  (`фабрика: docs/OPERATIONS.md`, README).
- **Маршрут (model route)** — фиксированный провайдер/модель прокси; текущий — `darkbloom/fp4`,
  без fallback; смена маршрута = изменение условий эксперимента (`фабрика: nix/_research/llm_proxy.py`,
  `фабрика: docs/OPERATIONS.md`).
- **Монитор кампании (dashboard / research-dashboard)** — локальный read-only web-монитор
  (порт 8788): стадии, документы циклов, критика, активность файлов; состояние читает, кампанию
  не запускает (`фабрика: dashboard/README.md`).
- **OpenSpec** — формат спек-ориентированной разработки следующей ревизии: proposal/design/
  specs/tasks + `openspec validate --strict` (`фабрика: nix/_research/OPENSPEC-WORKFLOW.md`).

## 3. Стенд и рамка исследования (dvarp)

- **DVARP** — Defense as Vector of Attack Research Platform: «защита как вектор атаки» —
  название платформы нашего прототипа/стенда (README, AGENTS.md); в старых доках репо
  «полигон» — см. канон 1.1.
- **Гвардрейл (guardrail)** — внешний контроль, встраиваемый между пользователем и агентом:
  фильтры входа/выхода, модели-детекторы, LLM-судьи; центральный объект оценки
  (`docs/guardrails-as-a-vector-of-attack.md` §3.2). Русская форма — «гвардрейл».
- **Рамка** — «каноническая рамка исследования»: границы, объекты, метрики
  (`docs/guardrails-as-a-vector-of-attack.md`); «рамка окупаемости» — её экономическая часть.
- **Канон** — зафиксированные неизменяемые решения рамки: один бизнес-процесс возвратов,
  5 инструментов, 3 модели-агента, 3 политики реакции, ориентир ≤16B
  (`docs/guardrails-research-design.md` §10); отклонения канона фиксируются в
  `docs/guardrails_requirements.md` §3.
- **Итерация 1 / итерация 2** — стадии проекта: доменное исследование (завершена) и реализация
  полигона (README «Статус»).
- **Бизнес-процесс** — моделируемый процесс обработки возвратов интернет-магазина; канон:
  это прототип (1.2).
- **Атакующая сторона / защищаемая сторона** — две стороны стенда (прототипа), изолированно
  взаимодействующие строго через канал (`docs/guardrails-as-a-vector-of-attack.md` §4.1).
  Канон: внутренние агенты (1.3).
- **Канал (единый текстовый канал)** — единственный способ взаимодействия сторон; все режимы
  ввода подключаются за одним интерфейсом канала (`docs/guardrails_requirements.md` FR-1.2/1.4).
- **Барьер интерфейса** — инвариант изоляции: атакующий не видит внутренностей защиты,
  защищаемая сторона — устройства атакующего; **research-mode** — маркированное исключение с
  расширенной обратной связью (`docs/guardrails-as-a-vector-of-attack.md` §4.2;
  `docs/guardrails_requirements.md` FR-1.3).
- **Исполнитель (executor)** — код, выполняющий только разрешённые действия и проверяющий
  права; «исполнитель не является гвардрейлом» (`docs/guardrails-as-a-vector-of-attack.md` §3.3/4.3).
- **Оценщик (evaluator)** — независимая сверка состояния БД с ожидаемым; «ответ модели — не
  доказательство» (`docs/guardrails_requirements.md` FR-1.18). В фабрике ту же роль играет
  арбитр/judge (`фабрика: nix/_research/COEVOLUTION.md` §A/§C).
- **Ground truth / дифф состояния** — истина по изменению состояния БД, а не по тексту агента
  (`docs/guardrails-research-design.md` §6).
- **Журнал (журнал затрат)** — единый лог событий и затрат по компонентам; «без него метрики
  не считаются» (`docs/guardrails_requirements.md` FR-1.17).
- **Эпизод** — единица взаимодействия, по которой фиксируются исход и стоимость
  (`docs/guardrails-as-a-vector-of-attack.md` §4.5). Не путать с эпизодом кампании (ЭК, 1.5) —
  единицей исследования в фабрике.
- **Снимок / хранилище состояния (snapshot)** — снятие и восстановление состояния перед каждым
  эпизодом; обязательно для парных прогонов (`docs/guardrails_requirements.md` NFR-2.1).
- **Ручная очередь (очередь ручных разборов)** — аналитическая модель (M/M/1 при одном
  операторе; M/M/c — Эрланг C — при K > 1) с явными допущениями (интенсивность потока,
  время обслуживания, число операторов) и сеткой чувствительности K×S; эскалации легальных
  и атакующих обращений общие; уход клиентов не моделируется (non-claim: клиент терпелив)
  (`docs/guardrails-as-a-vector-of-attack.md` §4.3, FR-1.15/1.16). **Живой оператор** —
  non-claim: «это модель, а не живой оператор» (`docs/guardrails-research-design.md` §3).
- **Эскалация** — передача случая человеку в ручную очередь; и канал убытка, и метрика
  `E(g) = w_L·E_L(g) + w_A·E_A(g)` (отчёт разделяет классы трафика: `E_L` — легальные эпизоды,
  включая FP; `E_A` — атакующие) (`docs/guardrails-break-even.md` §9.1).
- **Легальный поток / легальный трафик** — обращения законных клиентов, на которых измеряется
  ущерб от защиты (`docs/guardrails-break-even.md` §9.1).
- **Плагин / единый контракт гвардрейла** — гвардрейл подключается как плагин: вход (текст,
  контекст с происхождением, задача, вызов инструмента), выход — `allow/flag/block` или оценка
  (`docs/guardrails-as-a-vector-of-attack.md` §4.4; FR-1.5–1.9).
- **Место установки** — точка подключения гвардрейла: вход / выход / инструмент / контекст /
  среда / реакция (`docs/guardrails-as-a-vector-of-attack.md` §3.2).
- **Политика реакции** — что происходит при сигнале: продолжить / изолировать / уточнить /
  ручная проверка / безопасное завершение (`docs/guardrails-research-design.md` §4).
- **Конфигурация `g`** — комбинация «набор гвардрейлов + место + политика + пороги»;
  «конфигурация — данные, а не код» (`docs/guardrails-research-design.md` §4).
- **`g0`** — базовая линия «агент + исполнитель без гвардрейлов», обязательная точка отсчёта
  (README; `docs/guardrails-as-a-vector-of-attack.md` §5).
- **`g_proc`** — `g0` + сильные правила процесса, квоты, дедупликация; «обязательный соперник»
  (`docs/guardrails-as-a-vector-of-attack.md` §5).
- **Обязательные соперники** — дешёвые меры, с которыми обязательно сравнивать: правила
  процесса, текстовый детектор, LLM-судья (`docs/guardrails-as-a-vector-of-attack.md` §8.2).
- **Парные прогоны (paired runs)** — сравнение с/без атакующего трафика при одинаковых
  начальных условиях (`docs/guardrails_requirements.md` NFR-2.8).
- **Замороженный протокол (frozen protocol)** — пороги и конфигурация не меняются во время
  прогонов против адаптивного атакующего (NFR-2.10). **Pre-registration** — фиксация гипотез,
  конфигураций и метрик до итогового теста; добавленное после — «постфактум / post hoc»
  (`docs/guardrails-research-risks.md` §7).
- **Режимы `D` / `A`** — режимы атакующего; канон: только эти два (`docs/guardrails-as-a-vector-of-attack.md`
  §10): `D` — детерминированный корпус сообщений (многошаговые сценарии — заранее заданные
  последовательности, не зависящие от ответов агента), `A` — адаптивный LLM-агент (адаптивное
  построение диалога — только этот режим). Встречающееся в
  `docs/guardrails-research-risks.md` упоминание `T` неканонично (устаревшее, не определено).
- **Адаптивный атакующий** — противник, подстраивающийся под наблюдаемую обратную связь;
  бьёт по «недопредставленным механизмам» (`docs/guardrails-literature-review.md` §4.2).
- **Синтетика / синтетические данные** — «без реальных платежей и отправлений», без реальных
  PII (NFR-2.13); ограничение валидности результатов.
- **Clean controls (чистые контроли)** — сопоставимые по объёму легальные эпизоды для
  измерения ложных срабатываний (`docs/guardrails-as-a-vector-of-attack.md` §6.3).

## 4. Атаки, исходы, вред

- **Таксономия атак** — тройная разметка корпуса: механизм / цель / доставка
  (`docs/guardrails-as-a-vector-of-attack.md` §6.2).
- **`break` / `slow` / `burn`** — цели атакующего: исполненное нарушение или утечка;
  замедлить обслуживание; потратить ресурсы (`docs/guardrails-as-a-vector-of-attack.md`
  §7.1). `break` — единственный исход, проверяемый по состоянию. Эскалация — нормальное
  действие процесса и целью атаки не является (отклонения канона FR-1.21); форсированная
  эскалация легального кейса учитывается через FP (G-τ) и долю эскалаций.
- **Исходы эпизода: `ignored` / `refused` / `completed`** — фиксируются по состоянию БД, а не
  по тексту агента; атака может «безопасно» провалиться без явного отказа (README;
  `docs/guardrails-as-a-vector-of-attack.md` §7.3).
- **Исполненное нарушение** — действие, изменившее состояние сверх ожидаемого; центральная
  «единица вреда» (§7.3 рамки).
- **self-limited / defender-borne** — два класса вреда: расход самого атакующего (в экономику
  не входит) против расхода защищающейся стороны (входит) (§7.2; NFR-2.9).
- **Ложное срабатывание (false positive, FP)** — сигнал гвардрейла на легальном тексте; «прямой
  убыток». **Ложный отказ (over-refusal)** — отказ законному клиенту. **«Случайная атака»** —
  разговорный сценарий, когда FP бьёт по законному клиенту (`docs/guardrails-as-a-vector-of-attack.md` §6.3).
- **Потеря сюжета обращения** — метрика полезности: агент не довёл тему клиента до конца
  (§1/§8 рамки).
- **Канарейка / приманка (canary / decoy)** — маркерные элементы для детекта утечек и
  инъекций-приманок в документах (`docs/research-cycles/cycle_6.md` §3, `cycle_7.md` §5).
- **Payload** — «вредоносная нагрузка» атаки (`docs/guardrails-literature-review.md` §4.2).
- **Паспорт атаки (attack card)** — артефакт сценария: источник, возможности атакующего,
  граница доверия, нарушаемый инвариант, oracle, критерий успеха
  (`фабрика: nix/_research/EVALUATION-METHOD.md` §2).
- **Blind / implementation-informed** — происхождение сценариев атак: без знания кода защиты /
  с ним; legacy-сценарии помечаются implementation-informed (`фабрика: nix/_research/COEVOLUTION.md` §A.4).
- **Oracle** — независимый критерий успеха атаки по БД/журналам, не по словам агента
  (`фабрика: nix/_research/EVALUATION-METHOD.md`).
- **Held-out** — скрытый набор, не вскрываемый до фиксации конфигурации/автора
  (`docs/research-cycles/overall_cycle.md` «Дисциплина»).

## 5. Экономическая модель (break-even)

- **Экономический порог окупаемости `L*`** — цена одного исполненного нарушения, при которой
  данная конфигурация защиты окупается; итоговый формат ответа полигона вместо вердикта
  «выгодно/невыгодно» (README; `docs/guardrails-break-even.md` §9.2).
- **break-even** — общее название экономической модели/расчёта окупаемости.
- **`L_viol`** — цена одного исполненного нарушения; задаётся владельцем процесса
  (`docs/guardrails-break-even.md` §9.1).
- **`V(g)` / `R(g)` / `Q(g)` / `E(g)`** — метрики конфигурации: доля исполненных нарушений,
  необоснованных отказов, задержка легального потока (аналитическая, M/M/1 при одном операторе;
  M/M/c — Эрланг C — при K > 1, от измеренной `E(g)`), доля эскалаций — измеряется в парных
  прогонах (`docs/guardrails-research-design.md` §6).
- **`ΔNet(g)` / `F(g)` («трение») / `S(g)`** — чистый выигрыш, «ожидаемое трение» относительно
  `g0`, выигрыш в безопасности (§7 design-дока).
- **`C_guard(g)` / `C_ep(g)` / `C_refuse` / `C_queue` / `C_manual`** — стоимости: работы
  гвардрейлов, обслуживания атакующего трафика, необоснованного отказа, простоя в очереди,
  ручного разбора (`docs/guardrails-break-even.md` §9.1).
- **`w_A` / `w_L`** — доли атакующего и легального трафика в формуле (§7 design-дока).
- **У1–У4** — утверждения формального аппарата: доминирование, существование порога,
  немонотонность, бюджетное размещение (0/1-рюкзак) (§8 design-дока).
- **leave-one-out** — способ выделить «чистый расход» гвардрейла: убрать его и перегнать
  конфигурацию (`docs/guardrails-break-even.md` §9.3).
- **Pareto-фронт** — отчёт по осям «снижение нарушений × стоимость»; конфигурации вне фронта
  доминируются. **ROI-кривая** — семейство оптимумов `g*(B)` по бюджету; «ROI-кривая вместо
  рейтинга» (`docs/guardrails-research-risks.md` §5.6).
- **Недопустимая конфигурация** — увеличивает нарушения или делает очередь нестабильной;
  бракуется при любом `L_viol` (`docs/guardrails-break-even.md` §9.2).
- **`τ* = 1 − c_ℓ/c_w`** — порог эскалации из Act-or-Escalate; «буквально break-even… наш L*»
  (`docs/methodology/act-or-escalate.md` §4).
- **Рабочая точка / leakage / matched-FPR** — методологические заимствования Gate AI: фиксация
  порога, контроль утечек, сравнение при выровненном FPR (`docs/methodology/gate-ai.md`).

## 6. Дисциплина и артефакты кампаний

- **Brief (brief.md)** — входное задание цикла: цель, ресурс, дисциплина, приёмка; в
  verified-raw-data хранятся как `brief_1.md` … `brief_9.md`
  (`docs/research-cycles/verified-raw-data/incoming/`).
- **Progress (progress.md)** — поэтапный журнал агента-исследователя: «Блок 0…Блок N» +
  «Следующий шаг» (`docs/research-cycles/verified-raw-data/incoming/progress_*.md`).
- **Verified-raw-data (верифицированные сырые данные)** — каталог исходных артефактов
  кампании, хранимых «как есть» (README «Что внутри»).
- **Lessons / lesson_plan** — уроки предыдущих циклов и план их отработки на новом цикле
  (`docs/research-cycles/cycle_8.md` §1, `cycle_9.md` §3).
- **Workflow-contract.json** — контракт стадий конвейера (валидация артефактов стадии).
- **Prior-evidence** — доказательная база предыдущего цикла (review, pilot_results, candidates,
  sources).
- **memory.json** — артефакт стадии report: facts / failures / unknowns / next
  (`фабрика: nix/_research/README.md` §4).
- **MVP** — минимальный жизнеспособный прототип; обязательный артефакт каждого цикла.
- **Харнес (harness)** — канон: программная часть атакующего агента (АГ), управляющая
  выполнением операций, инструментами и расходованием ресурсов (1.5). В разборах методологий
  «Harness» — обвязка среды работы (environment + tools + логи), первый раздел каждого разбора
  (`docs/methodology/README.md`).
- **Trap-деталь** — обязательный раздел разбора «что ломается при reproduce»
  (`docs/methodology/README.md`).
- **Перенос / Адаптация / Непереносимо** — вердиктная триада разборов: что идёт в полигон
  напрямую / через адаптацию / непереносимо, с FR/NFR (`docs/methodology/README.md`).
- **Confirmation** — подтверждающий эксперимент на замороженном протоколе; без него вердикт
  цикла получает статус `inconclusive_*` (`docs/research-cycles/cycle_1.md` §5).
- **Holdout / dev (dev_calib)** — разделение выборок: «holdout не вскрывается до заморозки
  конфига» (`docs/research-cycles/overall_cycle.md`).
- **Honest accounting (честный раздельный учёт)** — неизвестные расходы помечаются `null`,
  «не заменяются нулём» (`docs/research-cycles/overall_cycle.md`).
- **Replay** — повторный независимый пересчёт исходов из raw-журналов; «проверка из чистой
  копии» (`docs/research-cycles/cycle_1.md` §5).
- **Дефект поставки** — повторяющийся паттерн кампании: обязательные артефакты
  (`dispatches.jsonl`, `sources.json`, `memory.json`, `pilot_results.json`) отсутствуют при
  «успешном» verifier (`docs/research-cycles/cycle_1.md` §5).
- **Fixtures (фикстуры)** — тестовые данные; «нельзя трактовать тестовые fixtures как
  подтверждённые исследовательские результаты» (`фабрика: README.md`).
- **Снимок (snapshot) / manifest.json** — неизменяемый слепок работы цикла с SHA-256-манифестом;
  критик получает read-only копию (`фабрика: nix/_research/README.md` §5).
- **Provenance** — происхождение артефактов: `source-manifest.json` (SHA-256 каждого
  перенесённого файла), `candidate/provenance.json` (`фабрика: docs/PROVENANCE.md`).
- **Harness-классы (COD / WEB / OPS / OFF / MAS / MEM)** — классы сред пула цикла 8: coding,
  browser, operations, office, multi_agent, persistent_memory (`docs/research-cycles/cycle_8.md`).
- **Проектные коды кандидатов (C8-OPS-GRB, C8-COD-TIG…)** — идентификаторы идей
  «цикл-среда-защита» (`docs/research-cycles/cycle_8.md` §1).
- **OPS-стенд** — переиспользуемый актив кампании: bwrap + prober + живые процессы + адаптеры
  (`docs/research-cycles/overall_cycle.md` «Готовые активы»); собственное имя актива, не
  канонический «стенд» (1.2).
- **Реестр гвардрейлов** — актив: 45 записей с pin/license/compatibility_probe
  (`docs/research-cycles/cycle_8.md` §1).
- **Runbook (D0-runbook)** — детерминированный скрипт-соперник, замороженный до первого
  запроса (`docs/research-cycles/cycle_8.md` §3).
- **Prober** — независимый монитор живых процессов с шагом 0.5 с (`docs/research-cycles/cycle_8.md` §3).
- **Compatibility_probe** — плановая проверка совместимости гвардрейла с маршрутом модели
  (`docs/research-cycles/cycle_9.md` §5).
- **Семейства политик циклов: `D0` / `H` / `B-*` / `Bstar`** — D0 — детерминированный baseline
  без LLM; H — искомая политика гипотезы; B-* — семейство бейзлайнов (B0–B6, B-hybrid,
  B-progress, B-cap, B-long, B-big, B-sys, B-snap, B-rolling); Bstar — лучшая выбранная
  бейзлайн-политика для confirmation (`docs/research-cycles/cycle_1.md`, `cycle_6.md`).
- **BEIS, TAQ** — кодовые имена гипотез циклов 6 и 7 (обе опровергнуты)
  (`docs/research-cycles/cycle_6.md`, `cycle_7.md`).

## 7. Процесс репозиториев

- **Ветвление `research` → `main`** — `research` интеграционная (default), `main` релизная и
  защищённая; изменения только через PR из `research` (AGENTS.md).
- **Issue ↔ доска** — каждый issue добавляется на доску DVARP Board
  (`CloudNative-urfu/projects/1`) и получает исполнителя; статусы `Backlog / Ready / In
  progress / In review / Done` (AGENTS.md).
- **Conventional Commits / commit-msg** — формат `<type>(<scope>): <description>`; типы
  `feat/fix/docs/build/ci/chore/test/refactor/perf/style/revert`; проверка локальным хуком
  commitizen и блокирующим CI (AGENTS.md, CONTRIBUTING.md).
- **Squash-merge** — слияние PR одним коммитом; заголовок PR должен быть conventional.
- **`FR-…` / `NFR-…`** — ID функциональных и нефункциональных требований к полигону
  (`docs/guardrails_requirements.md`); в deep_case извлекаются в `case/case.json`.
- **`research-mode`** — маркировка исследовательского режима стенда, отдельная от обычного
  сценария (FR-1.3; `фабрика: examples/deep_case.dvarp.md`).

## 8. Инфраструктура и эксплуатация

- **Sandbox / bwrap (bubblewrap)** — изоляция исполнителей: запись только в рабочем каталоге,
  кампания скрыта, материалы критика read-only (`фабрика: nix/_research/README.md` §5).
- **Preflight / doctor (`--live`)** — обязательная живая проверка перед запуском/продолжением
  кампании (MCP, модель, tool calling, SSE); сбой переводит кампанию в `blocked`
  (`фабрика: docs/OPERATIONS.md`).
- **Durable ledger (ledger.sqlite)** — SQLite-журнал исполнителя запросов: замороженный план и
  хеш, все попытки, HTTP-коды, ответы; повтор команды продолжает pending
  (`фабрика: nix/_research/WORKFLOW-V2.md`).
- **Квитанция (receipt)** — `.request.json` / `.receipt.json` в `cycles/NN/logs/`: задание,
  исполнитель и сообщённый расход; «операторская квитанция» фиксирует переход стадии
  (`фабрика: docs/DEEP_CASE.md`).
- **`usage_limit_reached` / `waiting_limit`** — распознанный лимит Claude: кампания переводится
  в ожидание сброса, попытки стадии не расходуются (`фабрика: docs/OPERATIONS.md`).
- **`blocked` / `exhausted`** — инфраструктурная остановка / исчерпанный бюджет без принятого
  кандидата (не успех) (`фабрика: docs/DEEP_CASE.md`).
- **Strict-black-box / research-feedback / believed_success** — режимы опыта атакующего:
  только наблюдаемые клиентом исходы vs разрешённый привилегированный скаляр;
  believed_success — вывод по тексту, не истинный исход по БД
  (`фабрика: nix/_research/COEVOLUTION.md` §B).
- **Лига замороженных версий** — этап C coevolution: матрица «новый атакующий × архивные
  защиты» и наоборот на закрытом held-out наборе (`фабрика: nix/_research/COEVOLUTION.md` §C).
- **Магазин / store / инфраструктура магазина** — предметный домен прототипа: заказы, тикеты,
  возвраты через версионируемые локальные API, вложения, операторские согласования, stateful
  платёжный эмулятор, асинхронные события и сверка (`фабрика: nix/_research/COEVOLUTION.md` раздел I).
- **Аспект (aspect) / nix-dots / Dendritic** — Nix-модуль в стиле nix-dots («Dendritic-аспект»),
  подключаемый хосту и пользователю; `agent-research-factory` выделен из конфиг-репозитория
  nix-dots (`фабрика: docs/INSTALL.md`, `фабрика: docs/PROVENANCE.md`).
- **Flake / devShell** — Nix-flake фабрики (экспорт модулей, CLI-пакетов, checks) и `nix develop`-
  окружение (`фабрика: flake.nix`).
- **CLI-пакеты** — `research-factory`, `research-experiment` (исполнитель запросов),
  `research-llm-proxy` (локальный OpenAI-compatible прокси), `research-dashboard`
  (`фабрика: flake.nix`).
- **Source-integrity / verify-source.py** — Nix check и скрипт побайтной сверки перенесённых
  исходников с манифестом (`фабрика: docs/VALIDATION.md`).
