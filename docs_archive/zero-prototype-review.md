# Обзор прототипа «zero» (dvarp-prototype / darp-prototype-runs)

- Дата: 2026-11-11
- Что анализировалось: локальный снимок `~/projects/dvarp-prototype` (репозиторий `darp-prototype-runs`, владелец geekiot) — архив из 9 сохранённых ревизий прототипа DARP (rev2, rev4–rev11; rev1/rev3 существовали, но в git не экспортированы).
- Сопоставлялось с: `docs/guardrails-as-a-vector-of-attack.md`, `docs/guardrails_requirements.md`, `docs/guardrails-research-design.md`, `iteration2-plan-draft.md`, `docs/research-cycles/` (overall + cycle_1..9), `docs/methodology/`.
- Метод: два независимых прохода (структура прототипа + выжимка целей исследования) с последующей свёркой. Полные отчёты — в приложениях A и B.

Роль прототипа в терминологии проекта (см. issue #14): **прототип** = наш симулируемый бизнес-процесс со связками для сбора данных для статьи — именно тот, который мы будем атаковать.

## 1. Итоговая оценка

**Рекомендация: дорабатывать существующее (rev11 как база) с ограниченной реорганизацией, а не переписывать с нуля.**

Соответствие нашим документам — очень высокое: прототип строился по нашему же канону (в `prototype/case/docs/` лежат наши `guardrails-as-a-vector-of-attack.md` и `guardrails-break-even.md`, `status.json` трекает 38/38 требований — наши FR-1.x/NFR-2.x).

Главный научный результат пока не получен: живых вызовов модели в rev10/rev11 не было, нарушения на заглушке не возникают → таблица `L*` = `no_safety_gain`/`unresolved`. Прототип в «foundation-фазе»; следующий научный шаг — живой срез атак на контуре rev11.

## 3. Ключевые расхождения и риски

1. **Измерение не начато**: rev10/rev11 — 0 живых вызовов; на заглушке нарушений нет → `L*` не посчитана. Для статьи это следующий шаг.
2. **Бюджет живых запросов** — реальный ограничитель (5 эпизодов HTTP 429 в кампании rev11).
3. **Адаптеры гвардов в основном бумажные**: живой контур проверен только на 1 внешнем детекторе (DeBERTa); адаптеры Qwen3Guard/Llama Guard 3/Granite Guardian/Presidio написаны, но ни разу не исполнены; фреймворковые рельсы (NeMo и т.п.) не проверялись вовсе (см. §6.3–6.4).
4. Заявленные пробелы (честно зафиксированы в `production-readiness.md`, `simplifications.json` — 264 записи): strict-black-box pending, синтетический auth, polling вместо push, уровни программы B/C — pending.
4. **Архитектура под ревизии, не под команду**: каждый проход = полная копия каталога; ~50% скриптов одноразовые (`rev*_*`, `mutate_rev*`); `verify_e2e.py` — монолит 1.4k строк; нет CI/линтера/окружения (пустые deps — сознательно для офлайн-воспроизводимости).

## 4. Что переиспользуемо / что нет

**Ценные активы:**
- корпуса (`corpus/`: v1, holdout_v2, heldout_v3, trusted_v7) — размечены, захешированы, с происхождением;
- `case/` — методология + 23 разбора литературы с хешами;
- пререгистрации (`preregistration-rev*.json` + deviations) и 129 паспортов атак (`attack-cards.json`);
- ядро `darp_range` (~31.6k строк, 1028 тестов): state_store, event_log, executor с границами, guard-контракт/плагины, metrics, manual_queue, evaluator, runner, isolation (bubblewrap-брокер);
- контур rev11 (`shop_svc`/`pay_emu`/`svckit`) — готовая поверхность под атаки на согласование/выплаты;
- верификационная дисциплина (`isolated_verify.sh`, мутанты, приёмка 17 ключевых требований; последний полный PASS: 109/109 шагов, ~53 мин).

**Плохо переносимое:** `verify_e2e.py` и ~35 ревизионных скриптов (~17k строк сценарной логики), ревизионные тесты (39 из 75 файлов), накопленные отчёты.

## 5. Минимальная реорганизация при доработке

1. Ядро `darp_range` — в версионированный пакет; кампании (brief/handoff/artifacts/ревизионные скрипты) — в данные рядом; прекратить полные копии каталога на каждый проход.
2. Обобщить мутационный фреймворк (сейчас ~28 копипастных скриптов).
3. Декомпозировать `verify_e2e.py` на регистрируемые шаги.
4. Пререгистрировать и провести живой срез на контуре rev11.

«С нуля» оправдан только при радикальной смене домена — и тогда разумнее как «rev12 с новой основой», сохраняя архив.

## 6. Модели, сеть, адаптеры и воспроизводимость

### 6.1. «Офлайн» ≠ «никогда нет сети»: два контура

- **Живые прогоны существуют и велись.** `report_cli live` через `RESEARCH_LLM_*` → внешний OpenAI-совместимый провайдер (Qwen). Реально гонялось: rev7 live-legal-slice (78 запросов), rev8 live-legal-slice-v2 (112/120 запросов, пререгистрация до первого запроса, H1 наблюдается — `report.md`), holdout_v2 корпуса — перефразы, сделанные Qwen; живой ONNX-вывод DeBERTa (298 текстов, rev3). HTTP 429 в `limit_history` кампании — упор в сессионный/недельный лимит провайдера, не «нет интернета».
- **Офлайн-verify — регрессия, а не вся наука.** 109/109 из чистой копии без сети (запрет сокетов, ast-аудит импортов только stdlib) — проверка воспроизводимости; записанные живые ответы (кассеты `llm/cassette.py`, `score_cache`) реплеятся офлайн, чтобы verify был hermetic. Дисциплина — по образцу RAGWarrant (docs/methodology/routeguard.md… ragwarrant.md).

### 6.2. Модели скачиваются — один раз, с фиксацией

`configs/oss/deberta-v3-base-prompt-injection-v2.lock.json`: HF-ревизия pinned (`90c9989`), sha256 всех 5 файлов, лицензия apache-2.0, версия onnxruntime/tokenizers/numpy зафиксирована nix-сторовыми путями. Скачивание однократное, дальше офлайн-реплей ровно этих весов (`scripts/oss_resource_check.py`: max_abs_diff 0.0 по 219 текстам).

### 6.3. Адаптеры гвардов: что проверено, что нет

- Проверено end-to-end: **1 внешний детектор** — protectai/deberta-v3-base-prompt-injection-v2 (адаптер `oss_deberta.py`, конфиг `g_in_oss` в lock, TPR 0.83/FPR 0.38 на v1, в таблице L*).
- Написаны, но **ни разу не исполнены**: адаптеры в `guard_plugins/adapters.py` на Qwen3Guard-Gen-4B, Llama Guard 3-8B, Granite Guardian 3.1-2B, Presidio (`enabled_by_default=False`; офлайн они превращаются в заглушки). Форматы вывода сверены с карточками моделей 2026-11-03, но живого прогона не было.
- 4 встроенных плагина — собственные офлайн-прокси, не «существующие гвардрейлы».
- **Фреймворковые рельсы (NeMo Guardrails, Guardrails-AI) не проверялись вообще** — это дыра относительно заявленной цели «оценить существующие гвардрейлы».

### 6.4. Контракт плагинов vs framework-рельсы: чего не хватает

Контракт (`guard_contract/`) — «детектор = сервис текст→сигнал» через `ChatModel` (`rt.complete()` с автоматическим начислением затрат в `C_guard`); классы развёртывания `("builtin", "self_hosted")`. Для рельсов-фреймворков нужно:

1. **Третий класс развёртывания** «library/framework» с декларацией зависимостей (extras + uv.lock, ленивый импорт). Механика частично готова: presidio-адаптер лениво импортируется и без библиотеки возвращает `AdapterUnavailable` — но класса в схеме нет.
2. **Маршрутизация LLM-вызовов рельса через `rt.complete()`** — иначе токены рельса не попадут в честный `C_guard` и break-even посчитается криво; фреймворки хотят владеть вызовом модели сами. Основная инженерная работа.
3. **Проверка инвариантов контракта** (запрет записи в БД, никаких бизнес-решений) на живом фреймворке — GuardHost уже детектит запись в БД, нужно прогнать.

Контракт расширяемый: рельс оборачивается в плагин «текст-в-сигнал», переделка не нужна.

### 6.5. Воспроизводимость: честная позиция прототипа

Полная воспроизводимость с LLM невозможна, и прототип это фиксирует явно (`artifacts/status.json`):

- «Повторное сэмплирование внешнего провайдера не воспроизводимо — это зафиксировано, а не скрыто»;
- «траектории при temperature 0 расходятся» (упрощение K2.7); модель pinается по `served_model_id`, `system_fingerprint` пишется в журнал;
- расхождение траекторий фиксируется как **дефект** (NFR-2.3): в живых срезах дефекты пар считались явно (4/9, 3/9).

Итоговый уровень: детерминизм всего, кроме LLM (хеши кода/конфигов/корпуса, побайтный реплей кассет), для LLM — пререгистрация до первого запроса + жёсткие лимиты + парные прогоны с фиксацией расхождений. Это научно достаточный стандарт; псевдоточная воспроизводимость живой LLM не достигнута ни в одной из 23 разобранных методологий.

`dvarp-prototype` — не сам прототип, а **архив снимков** (run-archive). Git-история: 9 коммитов `chore(research): preserve darp-revision-N…` (2026-11-06 … 2026-11-11). Структура каждой ревизии: `prototype/` (полный снимок кода), `review/` (независимая критика), `campaign/` (state.json, FINAL.md, cycles/), `source-manifest.json` (sha256 ~21 400 файлов), `export-manifest.json`.

### A.3. Модель данных и поток

Поток: **корпус → атаки → канал → агент → guardrails → исполнитель → БД → верификация → отчёт**.

1. `corpus/` — замороженный размеченный корпус («dirty English») по трём осям (delivery × goal × mechanism), с ground truth, происхождением (`adapted-from:nfr-2.7-example` и т.п.) и sha256 каждой записи. 24 пары «атака/чистый контроль» в v1; holdout-наборы критика отдельными версиями (v2 — перефразы через Qwen, v3 — закрытый набор критика).
2. `attackers/` — атакующая сторона за единственным текстовым каналом: режим D (детерминированный, по корпусу) и режим A (LLM-агент с памятью, лимитом попыток и обратной связью только из канала).
3. `channel/` — единственный текстовый канал, барьер интерфейса, отдельно маркированный research-mode; здесь же легальный клиент-симулятор (`legal_user.py`, `proposal_contract.py`).
4. `agent/` — агент возвратов (LLM с ровно 5 инструментами), не знает о гвардрейлах; есть детерминированная заглушка (`stub.py` с профилем уязвимостей) за тем же интерфейсом, что и живой Qwen (`llm/`, переменные `RESEARCH_LLM_*`, кассеты записи/воспроизведения).
5. `guard_contract/ → guard_plugins/ → guard_policy/` — контракт плагина (текст/контекст с provenance/доверенная задача → сигнал + затраты, запрет записи в БД), 4 встроенных офлайн-плагина (input-filter, tool-arg-validator, context-provenance, output-leak) + адаптер OSS-детектора DeBERTa (по умолчанию выключен), конвейер точек установки input/context/tool/output и политика реакции `continue/isolate/clarify/escalate/terminate`.
6. `tools/ → executor/` — 5 инструментов поверх исполнителя; три границы безопасности: `executor-boundary-1` (legacy), `executor-boundary-2` (rev6: серверные правила R1/R2/R5 в одной транзакции записи), `executor-boundary-2r` (rev7, текущая рекомендуемая основа v2r). Отпечатки границ захешированы в конфигах.
7. `state_store/` — синтетическая SQLite-БД магазина, снимок/восстановление перед каждым эпизодом; rev11 добавила отдельную БД контура со схемой v3.
8. `event_log/` — единый журнал событий и затрат с хеш-цепочкой (`prev`/`h`) и раздельным учётом сторон (attack/defense); докстринг честно признаёт, что in-process границей не является (утечка L1 воспроизведена и помечена).
9. `evaluator/` — сверка финального состояния БД с ground truth без чтения текста агента; исходы атаки `executed/refused/ignored`.
10. `manual_queue/` — дискретно-событийная модель очереди ручных разборов (операторы × время обслуживания).
11. `runner/` — оркестратор: снимок/восстановление, фиксированный seed, парные прогоны attacked/base по блокам, повторы для обнаружения расхождений, манифест прогона с хешами корпуса/конфигов/кода.
12. `metrics/` — ΔNet по формуле break-even, порог окупаемости L* на границах диапазонов цен, Pareto-фронт, стоимость на предотвращённое нарушение, интервалы Уилсона.
13. `report_cli/` — CLI сквозного офлайн-прогона всех конфигураций и живого прогона с жёсткими лимитами; `acceptance.py` — приёмка 17 ключевых требований (FR-1.2…NFR-2.9 из `case.json`).
14. `isolation/` (rev9–10) — атакующий в отдельном процессе под bubblewrap, брокер — единственный автор записи попытки (ребёнок шлёт только самоотчёт), 19 отрицательных OS-проб, матрица доступа с полем `enforcement`, `claim_level` в каждом манифесте.

Новое в rev11 (`shop_svc/`, `pay_emu/`, `svckit/`, ~2 000 строк): реально запускаемые процессы на 127.0.0.1 — аутентифицированный оператор approve/reject (HMAC-токен, перепроверка инвариантов в `BEGIN IMMEDIATE`), эмулятор выплат с идемпотентностью и append-only книгой, payout-worker с outbox/сверкой/монотонными переходами. Цепочка «эскалация → решение оператора → выплата → статус клиента» перестала быть фикстурой.

### A.4. Фиксация атак и верификация

- `artifacts/attack-cards.json` — 129 паспортов сценариев (возможности, доверенная граница, нарушаемый инвариант, oracle, легальная пара, `closed_at_write_by` для каждой из трёх границ).
- `artifacts/preregistration-rev{1..9}.json` + `-deviations.json` — пререгистрация протокола до измерений.
- `artifacts/status.json` — 38/38 требований, 29 implemented / 9 simplified, с evidence-путями.
- `artifacts/simplifications.json` — 264 записи «упрощение → почему → как улучшить».
- `artifacts/production-readiness.md` — карта «инвариант → реализация → тест → пробел».
- `scripts/verify_e2e.py` (1 362 строки) — сквозной verify: env → 1024 unit-теста → целостность (валидатор декомпозиции, хеш-заморозка конфигов/корпуса) → demo-пробы → e2e на seeds 7/8/9 → нагрузочный прогон → приёмка 17 ключевых требований → исторический контракт закрытых ревизий (`historical.py` — sha256 предрегистраций). Последний полный PASS: 109/109 шагов, 1024 теста, 17/17 ключевых, ~53 минуты, из чистой копии под `isolated_verify.sh` (netns без внешней сети + userns + снятые `RESEARCH_LLM_*`).

**Сильное:**

Процедура отработана (rev11 сделана агентами за ~2 дня, 0 живых запросов), но требует дисциплины.

### A.8. Аномалии и риски

1. Главный научный результат не получен: rev10/rev11 — 0 запросов Qwen; на v2r заглушка не даёт нарушений → таблица L* = `no_safety_gain`/`unresolved`. Полигон в foundation-фазе, эффект гвардрейлов не измерен.
2. Бюджет живых запросов — реальный ограничитель (5 эпизодов HTTP 429 в `limit_history`).
3. `production-readiness.md` — карта пробелов: синтетический auth, нет вложений, polling вместо подписанных push-событий, односторонняя изоляция in-process, strict-black-box и уровни программы B/C — pending.
4. Известные дефекты: денежные столбцы legacy плавают между прогонами (CPU-время), ResourceWarning в тестах, эквивалентный мутант MX3, ложная блокировка heldout_v3 ctl-04.
5. D11-S1 (payout recovery) сделан после полного verify — прежний PASS честно помечен historical.
6. Папка rev3 в git отсутствует при живых ссылках на неё (preregistration-rev3 внутри rev11) — разрыв экспорта.
7. Полное состояние кампаний (журналы, runs, сырые прогоны) — вне git на другой машине; git-экспорт неполон по замыслу.

### A.9. Взвешивание «доработать vs с нуля»

За доработку (rev11 как база): ядро `darp_range` библиотечное с высокой корректностью измерений; главный актив — методологическая трассируемость (264 упрощения, 129 паспортов атак, 9 пререгистраций, история критики), которую переписывание обнуляет; процедура ревизии отработана и дешёвая; целостность критична, потому что прототип будут атаковать (хеш-цепочки, брокер-как-единственный-писатель, независимый oracle).

Сценарий «с нуля» оправдан только при радикальной смене домена/модели измерений — тогда переиспользуются корпуса, case/, методология и форма пререгистрации, а разумнее делать это как «rev12 с новой основой», сохраняя архив.

## Приложение B. Выжимка целей исследования DVARP (агент-исследователь)

### B.1. Цель и гипотеза

1. Тема (рамка §1): «Защита агента как вектор атаки — полигон для оценки применимости существующих гвардрейлов в бизнес-процессе чатового агента: приносят ли они больше пользы, чем убытков». Собственные детекторы не разрабатываются — переиспользуются 20 OSS/self-hosted решений.
2. Основной вопрос: какие конфигурации гвардрейлов сохраняют безопасность и полезность процесса при той цене, которую создают; что именно сломалось (нарушение / необоснованный отказ / потеря сюжета), после чего, и сколько это стоило.
3. Формат вывода — экономический порог окупаемости L* (break-even): при какой цене исполненного нарушения `L_viol` конфигурация `g` окупается относительно `g0`; конфигурация окупается iff `L_viol > L*`.
4. Гипотеза новизны (§12): не найдено работ, которые в одном исследовании (а) оценивают конфигурации гвардрейлов внутри бизнес-процесса с измеримым исполненным нарушением как ground truth, (б) используют двухстороннюю схему с коммуникацией только через текстовый канал (и адаптивным атакующим), (в) считают стоимость защиты против предотвращённого ущерба с выдачей порога, (г) отделяют `self-limited` вред от `defender-borne`. Гэп подтверждён литобзором (снимок 15.10.2026).
5. Non-claims (research-design §1): не первый бенчмарк гвардрейлов, не первый DoS на гвардрейлах, не SOTA-детектор, не cross-lingual, не универсальная платформа. Claim language-agnostic, эмпирика — English-only («dirty English», NFR-2.7).
6. Границы первой версии (§14): один бизнес-процесс возвратов, 5 инструментов, 3 модели-агента (≤8B), 3 политики реакции, сначала one-shot-воздействие, затем короткие диалоги.

### B.2. Требования к прототипу/полигону

- Двухсторонняя схема с барьером интерфейса (FR-1.1–1.4); режимы ввода D (корпус) / A (атакующий агент) за единым интерфейсом канала.
- Бизнес-процесс: агент поддержки возвратов интернет-магазина на синтетических данных; результат — состояние локальной БД (FR-1.10–1.12); 5 инструментов.
- Исполнитель — не гвардрейл (FR-1.13–1.14); базовая линия `g0` = агент+исполнитель без гвардрейлов; `g_proc` = `g0` + правила процесса/квоты/дедупликация — обязательный «соперник».
- Гвардрейлы как плагины (FR-1.5–1.9): единый контракт, не меняют состояние и не принимают бизнес-решений; места установки вход/выход/инструмент/контекст/среда/реакция; конфигурация = данные.
- Ручная очередь (FR-1.15–1.16): эскалации идут в очередь с конечной пропускной способностью; параметры `c_w, c_sla, c_ab`, три режима нагрузки; вывод обязан пережить все (риск V5).
- Журнал и Оценщик (FR-1.17–1.19): honest accounting (unknown usage = null, не ноль); независимый Оценщик сверяет состояние БД с ground truth; исходы `completed / refused / ignored` (ATOM).
- Сценарии атак (FR-1.20–1.22): режимы D и A; таксономия по трём осям (механизм подрыва, цель break/slow/burn/shift, доставка); внешние источники — PICorpus/PIAtlas, AgentDojo, InjecAgent, garak, promptfoo; обязательные чистые контроли для измерения FP.
- Метрики (FR-1.23–1.24, §8): безопасность V(g), полезность R(g), непрерывность Q(g), эскалации E(g), детекция (TP/FP/FN/TN), экономика C_guard/C_ep → порог L*, Pareto-фронт, leave-one-out, чувствительность L* к ценовым допущениям.
- «Проверка результата атаки»: break подтверждается только изменением состояния сверх ожидаемого; slow/burn/shift — по журналу и парным прогонам; вред классифицируется `self-limited` vs `defender-borne`.
- NFR: snapshot/restore БД (2.1), seeds/хеши (2.2), расхождение траекторий = дефект (2.3), только OSS (2.4), локальный контур + pinned-версии (2.5), модели ≤8B (2.6), dirty-English корпус (2.7), парные прогоны (2.8), раздельный учёт расходов атакующего (2.9), заморозка защиты при адаптивном противнике (2.10), фиксированные лимиты атакующего (2.11), сравнение с g0/g_proc (2.12), синтетичность/без PII (2.13), артефакты (2.14), pre-registration.

Iteration2-plan-draft (актуальный план):
- Этап 1: v0 полигона («zero-версия», T5/T6 — разрабы «фабрика») — один end-to-end прогон `g0` без гвардов; приёмка — воспроизводимость из чистой копии (replay-дисциплина фабрики). Параллельно corpus-design (Матвей+Никита).
- Этап 2 (принцип «zero-версия раньше спек»): три спеки — `stack-decision.md` (Кирилл+Дмитрий), `run-protocol.md` (Матвей+Никита), `corpus-design.md` (50/50).
- Этап 3: pre-registration/заморозка. Этап 4: прогоны конфигураций, сводка L*/Pareto.
- Зафиксированные допущения: авто-исполнение возврата — конфигурация (knob `g_proc`), не аксиома; открытая «непонятка» №5 — базовая политика эскалации в MVP (`shift` имеет смысл только как прирост над ~30% самоэскаляций фона; кандидат — детерминированный hard-ignore + порог неопределённости θ).

### B.3. Циклы исследования (docs/research-cycles/)

Кампания велась через agent-research-factory (конвейер: постановка → пилот → эксперимент → независимая критика; модель qwen3.5-9b). Прототип «zero»/фабрика в циклах — не полигон DVARP: циклы 1–9 — автономные исследовательские кампании фабрики, финальный полигон в них не запускался.

- Overall: 9 циклов, 5 сквозных причин неудач (главные: детерминированное решение не хуже LLM-политики; неработающий интерфейс/маршрут; отсутствие обязательных ресурсов; атака редко достижима; дефекты поставки артефактов). Готовые активы: OPS-стенд (bwrap+prober+адаптеры Atomix/Progent/Agent-Git), B-sys, G-τ gate, replay-инфраструктура и honest accounting, реестр гвардрейлов (45 записей), спецификация 6 сценариев.
- Цикл 1 (fresh-context recovery): `inconclusive_confirmation_blocked`; 0 валидных адаптивных payload; побочно — replay-инфраструктура.
- Цикл 2 (semantic audit): `blocked_capability_no_confirmation`; 0/256 confirmation.
- Цикл 3 (остановка бесплодных повторов): live заблокирован квотой; scripted-контрасты: экономия ходов = потеря полезности; исполняемый offline MVP (45 тестов).
- Цикл 4 (reason-code repair): `inconclusive_f0_failed`; post-hoc ошибка D0 на отрицаниях.
- Цикл 5 (action-selector ID vs JSON): частичный dev; H-ID 12/12 F0, но уступает B-long/D0; 0 qualified family.
- Цикл 6 (BEIS): H1 опровергнута на holdout — B-sys 0.742 при 4.5k токенов vs BEIS 0.408 при 35k.
- Цикл 7 (TAQ): вердикта нет (операторская остановка, 1738/5160); на dev опровергнуты TAQ (20–22.5% ложных прерываний) и H1-sufficient.
- Цикл 8 (пул 6 сред): reject — need_for_llm=F (runbook 0.8 vs LLM 0.6), атака достижима в 1 из 3 кейсов; побочно — OPS-стенд и реестр гвардрейлов.
- Цикл 9 (спецификация 6 сценариев для полигона): не завершён — критик не выбрал идеи, 0 модельных вызовов; потеря кросс-модельности критика.

Последовательность работ: циклы фабрики → уроки c1-issue1 (полезность LLM не показана) и c1-issue2 (рабочий attack-controller/достижимость атаки) → перенос в DVARP: итерация 1 (доменное исследование, завершена) → итерация 2 (реализация полигона). Прототип DVARP появляется в iteration2-plan-draft как «v0/zero-версия» (этап 1), делает его «фабрика» (Кирилл+Дмитрий).

### B.5. Терминология

- «фабрика» / agent-research-factory: конвейер автономных кампаний — источник данных циклов; в iteration2-plan — «фабрика → zero-версия по имеющемуся», replay-дисциплина фабрики.
- «zero»/«zero-версия»: синоним v0 полигона — первый end-to-end прогон `g0` без гвардов (iteration2-plan; methodology/README «zero-версия фабрики»).
- «автооценщик»: термин в доках не встречается; используется «Оценщик» / Evaluator (рамка §4.3, FR-1.18) — независимая проверка исхода по состоянию БД, не по тексту агента.
- «внутренние/внешние агенты»: в такой формулировке не встречаются; термины проекта — «атакующая сторона» (режимы D/A) и «агент-исполнитель» на защищаемой стороне; в циклах фабрики — «исследователь» и «критик».
